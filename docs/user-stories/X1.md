# X1 Interface web

## Story 1

En tant que développeur, je veux discuter avec SENSAI dans une page web, afin de suivre ce que
fait l'agent (plan, outils, tokens) plus confortablement que dans le terminal.

Critères d'acceptation :
- `make web` construit l'interface, puis `sensai start:web` ouvre `http://127.0.0.1:8000/` ; si
  `sensai start:api` tourne déjà, la commande ouvre seulement le navigateur ; sans `web/dist`, elle
  s'arrête avec un message qui demande de lancer `make web`.
- La réponse s'affiche au fil du stream ; le plan ReAct et une carte par appel d'outil (nom, risque,
  durée, arguments et résultat dépliables) apparaissent dans le fil, au moment où ils arrivent.
- L'en-tête affiche le modèle, les tokens du tour par rapport à `[runtime] max_tokens`, et au survol
  le contexte du dernier appel et le total de la session ; le panneau de configuration liste le
  modèle, la température, la version du prompt, les limites du tour et les outils avec leur risque.
- La liste de gauche affiche les sessions enregistrées ; en ouvrir une recharge son historique.
- Un tour échoué reste affiché avec son erreur et la mention qu'il n'a pas été enregistré.

## Story 2

En tant que développeur, je veux garder la main sur l'agent depuis la page, comme dans la CLI,
afin que l'interface web ne contourne aucune protection.

Critères d'acceptation :
- Une écriture ou une commande ouvre une fenêtre avec le diff ou la commande ; rien ne s'exécute
  avant « Allow » ; « Refuse », `Échap` ou la fermeture de la page valent un refus, et l'outil
  refusé apparaît en échec dans le fil.
- Une question du modèle (X4) affiche ses options en boutons et un champ de réponse libre ; la
  réponse repart au modèle.
- Le bouton Stop interrompt le tour ; le texte déjà reçu est enregistré avec le statut
  `interrupted` (X2).
- Le bouton Fork d'un message crée une nouvelle session à partir de ce message et l'ouvre ; la
  session d'origine ne change pas.
- Le sélecteur de persona (A5) change de persona entre deux tours sans perdre l'historique ; il est
  refusé pendant un tour.

## Story 3

En tant que développeur d'un autre client (par exemple un client terminal), je veux une API qui
expose le même runtime que la CLI, afin de construire une interface sans dupliquer la logique.

Critères d'acceptation :
- `sensai start:api` sert `/api` et `/ws/sessions/<id>` sur `[api] host` et `port` et affiche les
  adresses ; un port déjà pris donne une erreur claire et le code 2 ; `Ctrl-C` arrête le serveur
  sans traceback.
- Un tour passe par le même assemblage que `sensai chat` (outils, MCP, guards, cache, mémoire) et
  est enregistré et journalisé de la même façon.
- Le WebSocket envoie les mêmes événements que ceux du journal ; un message vide, un type inconnu,
  du JSON invalide ou une réponse sans demande en attente renvoient une erreur sans couper la
  connexion ; une session inconnue est refusée avec le code 4404.
- `GET /api/sessions/<id>/messages` et le fork renvoient 404 pour une session ou un message
  inconnu.

## Tests

Les tests portent l'ID de la fonctionnalité avec `@pytest.mark.feature("X1")`.

- `tests/unit/test_api.py` (santé, configuration, sessions, stream d'un tour, approbation acceptée
  et refusée, annulation, persona, fork, interface servie à la racine, `start:api`, `start:web`)
- `web/src/lib/reducer.test.ts` (Vitest, `make web-test` : stream, cartes d'outil, refus, annulation,
  tour échoué, tokens, approbation, reconstruction de l'historique)
