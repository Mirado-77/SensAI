# T5 Sortie structurée

## Story 1

En tant que développeur qui intègre SENSAI dans un script, je veux obtenir une réponse en JSON
conforme à un schéma que je fournis, afin de la passer directement à un autre outil sans parser de
la prose.

Critères d'acceptation :
- `sensai ask --schema configs/schemas/bug_report.json "<question>"` écrit sur la sortie standard
  un JSON qui respecte le schéma, et rien d'autre.
- Si la première réponse ne respecte pas le schéma, le modèle reçoit les erreurs de validation et
  réessaie une seule fois (réglable avec `[structured] max_repairs`) ; la réparation est signalée
  sur la sortie d'erreur.
- Si la réponse n'est toujours pas conforme, la commande affiche les erreurs et sort avec le code 1,
  sans rien écrire sur la sortie standard.
- Un schéma introuvable, illisible ou invalide est refusé avant tout appel au modèle, avec le
  code 2.
- Chaque appel est journalisé (`run.started`, `structured.repaired`, `structured.failed`,
  `run.completed`) avec ses tokens.

## Story 2

En tant que développeuse qui laisse l'agent utiliser des outils, je veux que les arguments que le
modèle envoie à un outil soient validés contre le schéma de l'outil, afin qu'un appel mal formé
n'exécute jamais rien et que le modèle puisse se corriger.

Critères d'acceptation :
- Un appel d'outil dont les arguments ne respectent pas le schéma n'est ni exécuté ni soumis à
  approbation.
- Le modèle reçoit en retour la liste des erreurs (champ manquant, mauvais type) et peut renvoyer
  un appel corrigé dans le même tour.
- L'événement `tool.failed` porte l'erreur `invalid arguments` et apparaît dans le journal.
- Un outil dont le schéma de paramètres est invalide, ou n'est pas de type `object`, est refusé à
  l'enregistrement.
