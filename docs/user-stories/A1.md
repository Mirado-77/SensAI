# A1 Boucle ReAct bornée

## Story 1

En tant que développeur qui demande une correction à SENSAI, je veux voir un plan court avant
qu'il agisse, afin de savoir ce qu'il va faire et de l'interrompre si le plan est faux.

Critères d'acceptation :
- Avant le premier appel d'outil, le chat affiche `plan> <objectif>` suivi d'au plus
  `[react] max_plan_steps` étapes numérotées (5 par défaut).
- Le plan est un JSON validé par schéma (sortie structurée T5) : un objectif et des étapes
  courtes, sans champ de raisonnement libre.
- Une demande qui n'a besoin d'aucun outil donne un plan vide : rien n'est affiché et le modèle
  répond directement.
- Si le modèle ne produit pas de plan conforme après la réparation, le tour continue sans plan et
  `structured.failed` est journalisé.
- Le plan n'est pas enregistré dans l'historique de la session.

## Story 2

En tant que développeuse qui lit les logs d'une session, je veux que chaque étape de la boucle
(plan, action, observation) soit un événement, afin de suivre ce que l'agent a fait et pourquoi
il a corrigé sa trajectoire.

Critères d'acceptation :
- Le journal contient `react.plan` (objectif, étapes), puis pour chaque étape `react.action`
  (numéro, outils appelés) et `react.observation` (numéro, outil et erreur ou non).
- Quand un outil renvoie une erreur (traceback d'un test), l'observation porte `is_error` et le
  modèle peut relancer une action corrigée dans le même tour.
- La boucle reste bornée par `[runtime] max_steps`, `max_tool_calls` et `max_tokens` ; les
  tokens du plan comptent dans le budget du tour.
- `[react] enabled = false` supprime l'appel de planification et les événements `react.*`.

## Tests

Les tests portent l'ID de la fonctionnalité avec `@pytest.mark.feature("A1")`.

- `tests/unit/test_react.py` (plan, actions et observations, plan vide ou invalide, budget,
  désactivation, bornes, affichage dans le chat)
- `tests/unit/test_events.py` (vocabulaire des événements)
