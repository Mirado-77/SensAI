# T2 Commandes dans un bac à sable Docker

## Story 1

En tant que développeuse qui demande à l'agent de faire passer les tests d'un dépôt inconnu, je
veux qu'il lance les tests lui-même et lise la traceback, afin qu'il corrige le bug sans que je
copie la sortie à la main.

Critères d'acceptation :
- Le modèle choisit la commande selon le projet (`python -m pytest`, `npm test`, ...) et appelle
  `run_command` ; la commande tourne avec `sh -c` dans `/workspace`.
- Avant l'exécution, la CLI affiche la description, la commande, l'image, le dossier monté et
  `read-only, no network`, puis demande `Allow? [y/N]` (`[policy] exec = "ask"`).
- Le modèle reçoit stdout et stderr fusionnés, marqués comme contenu externe, suivis de
  « La commande a échoué avec le code N. » quand le code est une erreur. Pour `grep`, `rg`,
  `diff` et `test`, le code 1 n'est pas une erreur.
- Une sortie plus longue que `[sandbox] max_output_bytes` garde son début et sa fin, séparés par
  `[... N lines truncated ...]`.
- Sur `demo-repo/`, `python -m pytest` montre l'échec de `test_completion_rate_empty_list`
  (`ZeroDivisionError`) ; après la correction avec `edit_file`, les 8 tests passent.

## Story 2

En tant que développeuse qui laisse un modèle exécuter du code non fiable, je veux que la
commande soit isolée de ma machine, afin qu'un fichier piégé du dépôt ne puisse rien abîmer.

Critères d'acceptation :
- Le conteneur tourne sans root (uid 10001), sans réseau, système de fichiers en lecture seule,
  sans capacités, avec `no-new-privileges` et les limites `[sandbox]` `cpus`, `memory_mb` (sans
  swap) et `pids_limit`. Seul `/tmp` est accessible en écriture.
- Le dossier monté est dans `[files] allowed_roots` et en lecture seule : un chemin hors des
  racines est refusé avant de lancer Docker, et une écriture dans `/workspace` échoue avec
  « Read-only file system ».
- Une écriture refusée, un accès réseau ou un code 137 ajoutent une explication en français pour
  que le modèle ne réessaie pas la même commande.
- Après `[sandbox] timeout_s` (ou le `timeout_s` demandé s'il est plus court), le conteneur est
  tué ; le modèle reçoit la sortie déjà produite et « La commande a dépassé le délai et a été
  arrêtée. ». Ctrl-C pendant la commande tue aussi le conteneur.
- Si Docker est absent, si le démon ne répond pas ou si l'image manque, le chat démarre sans
  `run_command` et affiche la raison (par exemple « lance `make sandbox-image` »).
  `[sandbox] enabled = false` désactive l'outil sans vérifier Docker.

## Tests

Les tests portent l'ID de la fonctionnalité avec `@pytest.mark.feature("T2")`.

- `tests/unit/test_sandbox_docker.py` (options `docker run`, disponibilité de Docker, timeout,
  annulation)
- `tests/unit/test_run_command.py` (arguments, chemins, troncature, codes de sortie,
  explications, aperçu)
- `tests/unit/test_sandbox_tools.py` (branchement au démarrage du chat, repli sans Docker)
- `tests/unit/test_config.py` (section `[sandbox]`)
- `tests/integration/test_sandbox_live.py` (tests de `demo-repo/` dans la vraie image)
